# 14단계 — 제한형 관리자 코인 조정

## 단계 목표

고객 지원 보상이나 잘못 지급된 코인을 운영자가 안전하게 조정할 수 있게 합니다. 한
요청의 조정 한도, 경제 revision, 음수 잔액 방지, 멱등성 키와 변경 전후 감사 기록을
필수로 적용합니다.

## 관리자 전용 API

```http
POST /api/v1/admin/players/{playerId}/coins/adjust
X-Admin-Key: ...
Content-Type: application/json
```

```json
{
  "amount": 500,
  "reason": "고객 지원 티켓 CS-20260803-42 보상",
  "idempotencyKey": "CS-20260803-42-coin",
  "expectedEconomyRevision": 3
}
```

양수는 지급, 음수는 회수입니다. 0은 허용하지 않습니다. 플레이어 조회 응답의 최신
`economyRevision`을 보내야 하며, 게임 플레이나 다른 운영 작업이 먼저 재화를 변경하면
HTTP 409를 반환합니다.

## 조정 한도

기본 한도는 요청당 절대값 10,000코인입니다.

```text
AdminApi__MaxAbsoluteCoinAdjustment=10000
```

설정 허용 범위는 1~1,000,000입니다. 범위를 벗어나면 서버 시작을 거부합니다. 요청이
설정 한도를 넘으면 HTTP 422이며 경제 상태와 감사 원장은 변경하지 않습니다.

큰 보상이 필요할 때 한도를 임시로 높이거나 여러 요청으로 우회하지 않습니다. 별도
승인 절차와 전용 보상 기능을 만든 뒤 처리해야 합니다.

## 경제 도메인 검증

`PlayerEconomy.TryAdjustCoins`가 다음 규칙을 서버에서 검증합니다.

- 예상 revision과 현재 revision 일치
- 증감량이 0이 아님
- 조정 후 코인이 0 이상
- `long` 정수 범위를 초과하지 않음
- 성공 시 경제 revision 1 증가

클라이언트나 관리자 화면에서 계산한 최종 잔액은 신뢰하지 않습니다. 서버는 증감량만
받고 현재 DB 잔액에서 직접 결과를 계산합니다.

## 멱등성과 원자성

OperatorId와 `idempotencyKey` 조합은 기존 관리자 감사 원장의 고유 인덱스를 사용합니다.
타임아웃 후 같은 키로 재시도하면 최초 조정 결과를 `replayed: true`로 반환하고 코인을
다시 지급하거나 차감하지 않습니다.

같은 키를 계정 정지 또는 다른 플레이어 조정에 재사용하면 HTTP 409입니다. 경제 변경과
`admin_action_audits` 추가는 한 번의 `SaveChanges` 트랜잭션이므로 둘 중 하나만 저장될
수 없습니다.

## 감사 기록

성공한 조정은 다음 값을 영구 기록합니다.

- 작업명: `player.coins.adjusted`
- OperatorId와 멱등성 키
- 대상 플레이어 ID
- 변경 전 코인과 변경 후 코인
- 운영 사유
- 결과 economy revision
- 서버 UTC 시각

증감량은 변경 전후 값의 차이로 재구성할 수 있습니다. 실패한 검증 요청은 영구 감사
행을 만들지 않지만, 기존 HTTP 감사 로그에 상태 코드와 trace ID가 남습니다.

## 운영 절차와 복구

1. 플레이어 요약에서 현재 코인과 economy revision을 확인합니다.
2. 고객 지원 또는 사건 번호를 포함한 새 멱등성 키를 만듭니다.
3. 조정 금액과 최소한의 사유를 검토합니다.
4. API를 한 번 호출하고 타임아웃일 때만 같은 키로 재시도합니다.
5. HTTP 409면 최신 상태를 조회한 뒤 조정이 여전히 필요한지 다시 판단합니다.
6. 잘못 조정했다면 기존 감사 행을 수정하지 않고 반대 금액의 새 조정을 새 키와 사유로
   수행해 이력을 보존합니다.

현재 단계는 단일 관리자 키 권한입니다. 고액 조정이나 실제 결제 재화에는 관리자별
로그인, 역할 분리, 2인 승인과 일일 누적 한도가 추가로 필요합니다.

## 데이터베이스 변경
