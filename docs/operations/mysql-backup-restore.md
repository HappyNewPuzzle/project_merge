# MySQL 백업 및 복구 런북

## 백업 원칙

- 운영 DB 계정과 별도의 최소 권한 백업 계정을 사용합니다.
- 백업 파일은 암호화하고 애플리케이션 서버와 다른 저장소에 보관합니다.
- 일일 전체 백업과 바이너리 로그를 조합해 목표 RPO에 맞는 시점 복구를 준비합니다.
- 보관 기간, 암호화 키 접근과 삭제 정책을 조직 정책에 맞게 확정합니다.
- 백업 성공 로그만 믿지 않고 격리된 MySQL에서 정기적으로 복구 시험을 수행합니다.

## 논리 백업 예시

실제 비밀번호를 명령줄에 쓰지 말고 `MYSQL_PWD` 또는 승인된 비밀 주입 방식을 사용합니다.

```powershell
mysqldump --host DB_HOST --user BACKUP_USER `
  --single-transaction --routines --triggers --set-gtid-purged=OFF `
  merge_game > merge_game_YYYYMMDD_HHMMSS.sql
```

생성 파일의 크기와 체크섬을 기록하고 즉시 암호화 저장소로 이동합니다. 대규모 DB에서는
관리형 스냅샷이나 물리 백업 도구를 사용하고 같은 복구 검증 원칙을 적용합니다.

## 격리 복구 검증

1. 운영과 네트워크가 분리된 새 MySQL 8.0.36 인스턴스를 준비합니다.
2. 빈 `merge_game_restore_test` DB에 백업을 복원합니다.
3. 저장된 체크섬과 테이블 수, 핵심 행 수를 비교합니다.
4. 서버의 현재 마이그레이션을 적용해 스키마가 정상 전진하는지 확인합니다.
5. 읽기 전용 점검으로 플레이어, 경제, 보드, 원장 외래 키와 revision을 확인합니다.
6. 테스트 서버를 연결해 `/health`와 핵심 조회 API를 실행합니다.
7. 복구 시간, 복구 시점, 검증 결과와 발견된 문제를 기록합니다.

## 운영 복구

장애 범위와 마지막 정상 시점을 먼저 확정합니다. 쓰기 트래픽을 중지하고 원본 DB를 보존한
뒤 새 인스턴스에 복구합니다. 직접 덮어쓰지 말고 새 DB에서 검증한 다음 연결을 전환합니다.
경제 원장과 멱등 영수증이 선택한 복구 시점 이후 요청을 포함하지 않는지 확인하고, 유실
구간은 결제·운영 로그와 대조해 별도 보상 절차로 처리합니다.
